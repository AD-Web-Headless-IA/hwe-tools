## Description

Reusable **amenities / services / equipment** block for hospitality sites — the "what's included", "our facilities", "common spaces" and "equipment detail" sections. It renders one or more **labeled groups** of icon + label (+ optional description / link / footnote) items, in one of three layouts (card grid, checklist, inline list). Used on home, accommodation, services and facilities pages.

A `AmenitiesBlock.schema.ts` stub already exists in `packages/core-ui/src/schemas/` (minimal: `eyebrow?`, `heading`, `items[]`) and is re-exported from `schemas/index.ts`. This story **supersedes** that stub with the full co-located schema (`base-blocks/AmenitiesBlock/AmenitiesBlock.schema.ts`, re-exported from `schemas/`, per the GalleryBlock precedent — resolved decision 2026-06-19). The stub is a starting point, not the contract.

This story delivers **two units** (like US-001 delivered SwiperPrimitive + GalleryBlock):

1. **Hospitality icon set** — extend the curated `Icon` registry (`packages/core-ui/src/primitives/Icon/Icon.tsx`, **DEC-024**) with the ~25 icons the reference designs need (dumbbell, briefcase, coffee, utensils, clock, bed, fridge, microwave, tv, paw-print, snowflake, sparkles…). Without this the block is not usable in practice — today the registry has ~15 icons and unknown names render `null`.
2. **`AmenitiesBlock`** — the block in `packages/core-ui/src/base-blocks/AmenitiesBlock/`, consuming the `Icon` primitive.

## Visual variants (CVA — styling-only, NOT DEC-008 structural)

**Resolved with Cristina (2026-06-26):** the three layouts differ in Tailwind layout only — no divergent React hooks, no fundamentally different DOM trees — so they are a **CVA `layout` variant**, not the DEC-008 structural-folder layout (contrast GalleryBlock, which genuinely needed structural variants for Swiper hooks). The block is a **Server Component**; the only interactive piece (a collapsible group) is isolated in one small `'use client'` island.

| Layout (`layout`) | Description | When to use | Technique |
|---|---|---|---|
| `grid` (default) | Bordered cards, icon centered on top + label below (+ optional description). Reference img 1 left, img 3. | Common spaces, facilities, highlighted services | CSS Grid, `columns` knob (2/3/4) |
| `checklist` | Uniform check glyph + bold label in a vertical list. Reference img 1 right. | "Services included", quick yes/no feature lists | Flex rows; ignores per-item `icon` (uses one check) |
| `list` | Icon (optionally in a circle/badge) + label in rows, multi-column. Reference img 2. | Long equipment lists ("what's included", "equipment detail") | CSS columns / grid, `columns` knob |

**Per-group layout override.** A single block instance can mix layouts across groups (reference img 1 shows a `grid` group beside a `checklist` group). Each group may set its own `layout`; groups without one inherit the block-wide default from config. See resolved decision #2.

**Collapsible group (the one interactive piece).** Any group may set `collapsible: true` to render behind an expand/disclosure toggle (reference img 2, "Equipamiento en detalle ▼"). This is the **WAI-ARIA Disclosure pattern**, implemented as a small `'use client'` sub-component (`CollapsibleGroup`) — reuse the approach already in `BookingSearchBlock/disclosure/` (AccordionDisclosure). The rest of the block stays server-rendered.

## Functional requirements

### SEO
- Semantic structure: `<section>` → optional heading at `headingLevel` → per group an optional sub-heading + a `<ul role="list">` of `<li>`. (Tailwind's `list-style:none` strips list semantics in Safari/VoiceOver — restore with explicit `role="list"`.)
- Items with `href` render a real `<a>`; otherwise plain text.
- Heading hierarchy: block `heading` at `headingLevel` (default 2), group headings one level deeper, never `<h1>`, never hardcoded.
- **No JSON-LD by default** — AmenitiesBlock is presentational. (For an accommodation page, schema.org `amenityFeature` / `LocationFeatureSpecification` is the **template's** responsibility, emitted alongside the `LodgingBusiness`/`Accommodation` entity — not this block's.) Note this explicitly so it is a decision, not an omission.

### Accessibility (non-negotiable)
- Lists: `<ul role="list">` + `<li>` per item.
- Icons are **decorative** (`aria-hidden`, no `label` on `Icon`) because the visible text label carries the meaning. (Exception: the `checklist` check may keep an `aria-label` only if the check itself conveys "included" with no other text — here the label exists, so decorative.)
- Collapsible group → **WAI-ARIA [Disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)**: toggle is a `<button>` with `aria-expanded` + `aria-controls` pointing at the group region; content region `id` matches. Keyboard: Enter/Space toggles. Focus stays on the button.
- `prefers-reduced-motion`: the expand/collapse transition reduces to instant.
- `toHaveNoViolations` (vitest-axe) for every layout + the collapsible open/closed states.

### Performance
- Server Component by default — no JS shipped except the `CollapsibleGroup` island, and only when a group is `collapsible`.
- Icons via the curated registry (DEC-024) → tree-shaken; only registered icons are bundled. No icon font, no full lucide import.
- No images, no external dependencies.

### Server/client boundary
- **Server shell** (RSC, no `'use client'`): parses content + config, renders all headings, lists, items, links and the static (non-collapsible) groups. All SEO-relevant content is in the SSR HTML.
- **Client island** (`'use client'`): only `CollapsibleGroup` — wraps a group's pre-rendered markup with the disclosure toggle + open/close state. The group's items exist in SSR HTML even when collapsed (CSS-hidden, not unmounted) so crawlers/AT see them.

## Styling
- **Zero CSS per block** — Tailwind utilities + theme tokens only. Card borders, circle/badge backgrounds, gaps, check colour all from tokens (`--color-border`, `--color-surface`, `--color-accent`, `--color-secondary`, spacing scale). No hardcoded colours/spacing.
- `iconStyle: badge` uses the accent token for the disc (img 3 yellow = `var(--color-accent)`), so each client recolours it through its own theme automatically (platform base block = token-driven neutral, per US-001 archive note on base-block neutrality).
- Client overrides scope: `[data-block="amenities"]` (client repo's dedicated CSS file, never `globals.css`).

## Resolved decisions

1. **Layouts → CVA, not structural (DEC-008).** Cristina, 2026-06-26: grid/checklist/list differ in Tailwind layout only — "algunas pueden ser con CSS". No divergent hooks/DOM trees, so no `index.ts` resolver + subfolders. The single interactive concern (collapsible group) is isolated in a `'use client'` `CollapsibleGroup`, keeping the block a Server Component. This is the deliberate inverse of GalleryBlock.
2. **Multiple groups + per-group layout → `groups[]` in content, with per-group `layout` override. ✅ Ratified (Cristina, 2026-06-26 — "Alt A").** One instance models the side-by-side heterogeneous sections (img 1: grid + checklist; img 2: list + collapsible detail). Block-wide `layout`/`columns`/`iconStyle` defaults live in config; a group may override `layout` and set `collapsible`. The boundary call is **confirmed**: per-group `layout`/`collapsible` live in *content* (not config) because they describe each group's structure and vary within one payload — a deliberate, documented deviation from "all presentation in config", justified by heterogeneity (expressing img 1 in a single instance). **Rejected alternative (for the record):** block-level `layout` in config + img 1 as two adjacent instances — discarded because it can't express img 1 as one block.
3. **Width / background → full-bleed `background` colour token in config; content stays contained.** Cristina, 2026-06-26: "el fondo puede tener un color también". The section background spans edge-to-edge via a theme token; the content keeps the site `--width-container`. No separate "full vs contained content width" knob in v1.
4. **Icon registry expansion bundled into this story — curated-only.** Cristina, 2026-06-26: extend the curated `Icon` registry (DEC-024) with a hospitality set so the block is usable on delivery (the reference icons are not registered today). Custom SVGs in `src/icons/` only for icons lucide lacks. **Reconfirmed 2026-06-26:** icons come from a *curated* registry only — no open/dynamic library access and no per-item emoji/SVG escape hatch. `AmenityItem.icon` is always a registered registry name; an icon a client needs is added to the registry, not passed inline.
5. **`icon` and `heading` optional; `checklist` uses a uniform check.** An item needs only a `label`; the `checklist` layout renders one check glyph and ignores per-item `icon`. Block/group headings are optional (a preceding block may own the heading).
6. **No JSON-LD by default.** Presentational block. schema.org `amenityFeature` for accommodation pages is the template's concern, not this block's — recorded as a decision, not an omission.
