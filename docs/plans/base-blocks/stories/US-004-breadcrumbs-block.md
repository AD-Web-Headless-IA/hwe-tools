# US-004 — Implement BreadcrumbsBlock (route-derived breadcrumb trail + BreadcrumbList JSON-LD)

> **Epic:** base-blocks · **Status:** Draft (awaiting team review) · **Source:** Cristina request 2026-06-30 — "breadcrumbs de las páginas", trail auto-derived from the route hierarchy, default `slash` separator, `schema.org/BreadcrumbList` JSON-LD.
> **Generated by** `/generate-block-story`. Paths are relative to the **hwe-core repo root** (base blocks live in `@hwe/core-ui`); architecture/contract/spec docs live under the mounted `hwe-tools/` submodule.

## Description

A small navigation block that renders the **breadcrumb trail** for the current page — the ancestor path from the home page down to the page the visitor is on (e.g. `Home / Accommodation / Suite with hot tub`). It is the canonical secondary-navigation + SEO affordance for deep hospitality pages (accommodation detail, category, services sub-pages).

The trail is **derived automatically from the current route** (Cristina's decision 2026-06-30) — the editor does **not** hand-author it per page. Two sources combine:

1. **The route** (`usePathname()`) gives the ordered path segments — this is the "where am I" signal and the reason the block is automatic with zero per-page wiring.
2. **The tenant `nav` tree** (`useTenant().nav.links`, including nested `children`) is the **label source**: a segment whose `href` matches a nav link/child uses that link's human label. Segments not present in the nav tree fall back to a humanized slug (`suite-deluxe` → "Suite Deluxe") or to an explicit `labelOverrides` entry from the block content (the escape hatch for dynamic detail routes).

This mirrors the existing **Navbar** precedent: `Navbar` is a `'use client'` chrome component that already reads `TenantConfig.nav.links` (`packages/core-ui/src/layout/Navbar/Navbar.tsx`). BreadcrumbsBlock reuses that exact data, so it introduces **no new tenant plumbing** for labels.

The block ships three units:

1. **`buildBreadcrumbTrail`** — a **pure, React-free, DOM-free resolver** (`pathname + navLinks + options → BreadcrumbItem[]`). This is the testable heart of the block (TDD), unit-tested without rendering — the same separation US-003 used for `createBookingLink` and GalleryBlock used for `buildImageGalleryJsonLd`.
2. **`buildBreadcrumbListJsonLd`** — a pure `BreadcrumbList` JSON-LD builder, mirroring `GalleryBlock/shared/jsonLd.ts`.
3. **`BreadcrumbsBlock`** — the registered block that resolves the trail, renders the semantic `<nav>/<ol>` and the JSON-LD `<script>`.

## Visual variants

The breadcrumb DOM is **identical** across separators — `<nav><ol><li>…` — only the divider glyph changes. Per the US-002 ratified rule (decision #1: grid/checklist/list are a **CVA axis, not DEC-008 structural variants** because they differ in styling only), the separator is a **CVA/config axis, not a DEC-008 structural variant**. No `index.ts` resolver, no per-variant subfolders. Single `BreadcrumbsBlock.tsx`, exactly like `AmenitiesBlock`.

| Separator (`config.separator`) | Rendering | Notes |
|---|---|---|
| `slash` (**default**) | `/` between items, rendered as a decorative CSS/`aria-hidden` glyph. | The requested default. |
| `chevron` | `Icon name="chevron-right"` (already registered, `Icon.tsx:57`), `aria-hidden`. | Most common in hospitality. |
| `none` | No glyph (spacing only). | For designs that separate by spacing/colour. |

Cosmetic add-ons (config, not structural):
- `homeIcon` — render the first (home) crumb as `Icon name="home"` (already registered, `Icon.tsx:71`) instead of text.
- `size` — `sm | md` text scale (CVA axis), default `sm` (breadcrumbs are small by convention).

> **Deferred (not v1):** a fundamentally different **mobile "back to parent"** layout (only the parent crumb + a back arrow, different DOM) *would* qualify as a DEC-008 structural variant. Cristina chose "variantes según diseño" — so **defer** until a Figma reference defines it; add it then as a structural variant `back` with the resolver layout. v1 ships the single inline trail with a responsive **collapse** (see `collapseAfter`) for long trails.

## Content fields (Layer 1 — `BreadcrumbsBlock.schema.ts`)

The trail is auto-derived, so content is **almost empty by design** — it carries only the label-resolution knobs and an optional full manual override.

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `homeLabel` | string | no | `"Home"` | Label for the root crumb. Localizable. |
| `showHome` | boolean | no | `true` | Whether the home/root crumb is prepended. |
| `labelOverrides` | `Record<string, string>` | no | `{}` | Escape hatch: maps a path (`/accommodation/suite-deluxe`) **or** a bare segment (`suite-deluxe`) to a label, for dynamic/detail routes whose label is **not** in the nav tree. Resolution order: explicit override → nav-tree label → humanized slug. |
| `items` | `BreadcrumbItem[]` | no | — | **Full manual override.** When present (≥1), the block renders this exact trail and skips auto-derivation entirely. The safety valve for pages where the route ≠ the desired trail. |

**`BreadcrumbItem` (nested):**

| Field | Type | Required | Notes |
|---|---|---|---|
| `label` | string (min 1) | **yes** | Visible text. |
| `href` | string | no | Link target. Omit on the current (last) item — it renders as `aria-current="page"` text. |
| `isCurrent` | boolean | no | Marks the current page; defaults to "the last item" when omitted. |

> Zod boundary rules (per `block-architecture.md` §1): `label` is `.min(1)`; `items` (when given) is `z.array(BreadcrumbItem).min(1)`; everything else `.optional()` with `.default(...)` where a default exists. Type is always `z.infer` — no hand-written interfaces, no `any`.

## Behavioral config (Layer 3 — `BreadcrumbsBlock.config.schema.ts`)

| Field | Type | Default | Notes |
|---|---|---|---|
| `separator` | enum `slash \| chevron \| none` | `slash` | Divider style (CVA axis). |
| `homeIcon` | boolean | `false` | Render the home crumb as the `home` Icon. |
| `currentAsLink` | boolean | `false` | If `true`, the current page is also a link; default is `aria-current` text (APG-recommended). |
| `size` | enum `sm \| md` | `sm` | Text scale (CVA axis). |
| `collapseAfter` | number (int ≥ 3) | — | When the trail exceeds N items, collapse the middle into a single `…` crumb (keeps first + last), per APG long-trail guidance. Omitted = never collapse. |

Config is parsed defensively at the block boundary (`safeParse(raw ?? {})` → fall back to `parse({})`), exactly as `AmenitiesBlock.parseConfig` and `GalleryBlock` do.

## Functional requirements

### SEO (non-negotiable)
- **JSON-LD `BreadcrumbList`** via `buildBreadcrumbListJsonLd(trail, origin)` — pure builder mirroring `GalleryBlock/shared/jsonLd.ts`. Shape:
  ```json
  { "@context": "https://schema.org", "@type": "BreadcrumbList",
    "itemListElement": [
      { "@type": "ListItem", "position": 1, "name": "Home", "item": "https://…/" },
      { "@type": "ListItem", "position": 2, "name": "Accommodation", "item": "https://…/accommodation" },
      { "@type": "ListItem", "position": 3, "name": "Suite with hot tub" } ] }
  ```
  - `position` is 1-based and contiguous. The **last** item SHOULD omit `item` (Google's documented convention for the current page).
  - `item` should be an **absolute** URL. Origin sourcing is **Open question #2** (no `siteUrl` exists on `TenantConfig` today). v1: build absolute from an optional `TenantConfig.siteUrl` if present, else emit path-relative `item` and flag.
  - JSON-LD must reach the crawler — see **Open question #1** for the SSR vs client-rendered decision. The pure builder is identical either way; only *where* the `<script>` is emitted changes.
- **Semantic HTML (binding, W3C APG Breadcrumb pattern):** `<nav aria-label="Breadcrumb">` landmark → `<ol>` (ordered, not `<ul>`) → `<li>` per crumb. Current page: `aria-current="page"`. No `<h1>` (breadcrumbs have no heading).
- Separators are **decorative**: render via CSS `::before`/`aria-hidden` so they are absent from the accessibility tree and from the copied text.

### Accessibility (non-negotiable)
- W3C APG [Breadcrumb pattern](https://www.w3.org/WAI/ARIA/apg/patterns/breadcrumb/): `nav[aria-label="Breadcrumb"]` + `ol` + `aria-current="page"` on the current crumb.
- Links are real `<a>` in natural tab order — no custom keyboard handling needed.
- Decorative separators and the optional home icon are `aria-hidden` (the `Icon` primitive already sets `aria-hidden` when no `label` is passed — `Icon.tsx:119-123`).
- `collapseAfter` ellipsis: the `…` is a real, focusable disclosure only if it expands interactively; for v1 the collapsed middle items remain in the DOM `aria-hidden`/visually-hidden so the full trail stays available to AT, or are simply omitted with the ellipsis labelled — pick one and test it.
- `toHaveNoViolations` (vitest-axe) for: default `slash`, `chevron`, `homeIcon`, the collapsed state, and the manual-`items` path.
- No animation → `prefers-reduced-motion` is N/A.

### Performance
- Pure resolver + pure JSON-LD builder — zero runtime dependencies, tree-shakeable.
- **No new npm dependency.** Icons reuse the existing `Icon` primitive (`chevron-right`, `home` already registered — `Icon.tsx`). `usePathname` is from `next/navigation` (already a peer).
- If implemented as a client component (Open question #1), the JS footprint is minimal (one small component); separators are CSS, not extra DOM nodes.

## Styling
- **Zero CSS per block** — Tailwind utilities + theme tokens only, no hardcoded colours/spacing. Use the same token utilities seen across the repo: `text-foreground`, `text-muted-foreground`, `text-accent`, `max-w-[var(--width-container)]`, `font-*` (NOT hex, NOT inline `style` colours except runtime-dynamic).
- Token-neutral base block: the per-client look (link colour, separator colour, hover) comes from that client's tokens / Level 2–3 overrides — never block CSS (GalleryBlock/AmenitiesBlock precedent, Cristina 2026-06-19).

## Open questions for review
1. **Route access + SSR JSON-LD — the one architectural decision (candidate DEC).** No block reads the route today, and the repo convention is **SSR** JSON-LD (`GalleryShell` emits the `<script>` server-side; the geo-llm audit checks SSR). But the only **truly automatic, zero-per-page** route source in this App Router setup is `usePathname()` — a **client** hook — and the nav-tree label source lives in the **client** `TenantProvider`. There is no `middleware.ts` in the repo. The trade-off:
   - **Option A (recommended for v1): client component.** `'use client'`, `usePathname()` + `useTenant()` + the pure resolver; renders the `<nav>` **and** the JSON-LD `<script>`. Pros: genuinely zero-config auto, reuses the Navbar nav-tree pattern, buildable now with no platform change. Con: JSON-LD is client-rendered — Googlebot executes JS and indexes it, but the SSR-only audit will flag it.
   - **Option B (SSR-clean, needs a platform change): server component.** Ship a root `middleware.ts` in `hwe-template` that sets an `x-pathname` header; the block reads it via `next/headers` and emits JSON-LD SSR. Requires the nav tree to be available **server-side** (today it is client-only via `TenantProvider`) — so either pass labels through block config or add a server-readable tenant source. More moving parts; a real DEC.
   - **Recommendation:** ship **Option A** now (the pure resolver + builder make Option B a later, non-breaking swap), and open a DEC — *"block route-awareness + SSR breadcrumb structured data"* — to decide whether to invest in Option B. Ratify before `/propose`.
2. **Absolute-URL origin for JSON-LD `item`.** `TenantConfig` has no `siteUrl`. Add an optional `TenantConfig.siteUrl` (clean, reusable for other structured data) or derive from Next `metadataBase`? v1 falls back to relative `item` + a flag if origin is unknown. Confirm.
3. **Mobile "back" layout.** Cristina chose "variantes según diseño". If a Figma reference later defines a compact mobile back-to-parent layout (different DOM), add it as a **DEC-008 structural variant** then. v1 = inline trail + `collapseAfter`. Confirm this is acceptable for v1.
4. **`labelOverrides` granularity.** Keyed by full path *and* bare segment (current spec), or full path only? Bare-segment keys are terser but can collide across routes. Confirm.
