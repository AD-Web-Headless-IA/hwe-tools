v1.0 — Hospitality Web Platform

HWP Platform

Plataforma multi-tenant para webs de camping y hotel. De Figma a producción, con IA, para hasta 300 clientes.

Visión general

HWP es el producto de Septeo Hospitality que reemplaza las webs WordPress individuales por una plataforma unificada. Cada web de cliente se construye combinando bloques reutilizables con la identidad visual propia del cliente.

🧱

Bloques compartidos

Un catálogo de ~25 bloques (hero, galería, reservas, FAQ...) que todos los clientes comparten. Cada cliente los personaliza con sus colores, fuentes y, si necesita, su propio JSX.

🎨

Tokens como identidad

Los colores, fuentes, radios y sombras de cada cliente se definen como tokens. Un mismo bloque se ve completamente diferente entre un camping teal y un hotel dorado.

🤖

IA integrada

11 agentes de IA especializados (arquitecto, implementador, revisor, auditor SEO, seguridad...) que garantizan calidad en cada paso del desarrollo.

🚀

300 clientes independientes

Cada cliente tiene su propio repositorio y deploy en Vercel. Un bug en un camping nunca afecta al hotel de al lado.

Arquitectura

HWP tiene dos mundos: el monorepo de plataforma (donde vive el código compartido) y los repos de cliente (donde vive cada web individual). Los clientes consumen los paquetes de la plataforma via npm.

📦 hwp-platform/ (monorepo)
↓ publica @hwp/* via npm
📦 site-camping-mer/ (repo independiente)
↓
📦 site-hotel-balneario/ (repo independiente)
↓
📦 site-camping-sol/ (repo independiente)
↓ ... hasta 300 repos
¿Por qué repos separados? Escalabilidad (300 repos pequeños > 1 repo enorme), aislamiento (un dev solo clona su proyecto), deploys independientes (un bug en un cliente no bloquea a otro). Decisión: DEC-011.

Sistema de bloques

Un bloque es una sección reutilizable de una página web: un hero, una galería, un formulario de contacto, una sección de reseñas. Cada bloque tiene un contrato de datos (schema Zod) y una implementación visual (React + Tailwind).

Dónde vive cada cosa

PiezaUbicaciónQuién la toca
Schema Zod (contrato de datos)@hwp/core-ui/schemasEquipo de plataforma
Base-block (implementación de referencia)@hwp/core-ui/base-blocksEquipo de plataforma
Bloque del cliente (personalizado)site-{slug}/src/blocks/Developer del cliente
Composición (montaje de página)site-{slug}/src/compositions/Developer del cliente

Tres niveles de uso

Level 1 — Re-export (~70%)

El cliente usa el base-block tal cual. Los tokens (colores, fuentes) lo hacen suyo. Cero código custom.

export { HeroBlock }
  from '@hwp/core-ui/base-blocks';

Level 2 — Slots (~20%)

El cliente personaliza piezas concretas (cómo se ve el título, el botón) sin reescribir todo el bloque.

import { HeroBlock as Base }
  from '@hwp/core-ui/base-blocks';
export function HeroBlock({ content }) {
  return <Base content={content}
    slots={{ heading: miHeading }} />;
}

Level 3 — Full custom (~10%)

El cliente escribe su propio JSX completo, usando solo el schema compartido para los datos.

import type { HeroBlockContent }
  from '@hwp/core-ui/schemas';
export function HeroBlock({ content }) {
  return <section>
    {/* JSX totalmente custom */}
  </section>;
}

Cadena de resolución

Payload envía layout[] con tipo "HeroBlock"
↓
BlockRenderer busca en clientBlocks (registry.ts del cliente)
↓ ¿Encontrado?
Sí → usa la implementación del cliente
↓ ¿No encontrado?
Fallback → usa base-block de @hwp/core-ui

Las 4 capas de un bloque

Cada bloque tiene hasta 4 capas. La primera es obligatoria; las demás se añaden según la complejidad del bloque.

L1 — Schema
L2 — Variants
L3 — Config
L4 — Adapter

Layer 1 — Content Schema (siempre)

Define qué campos tiene el bloque. Es un schema Zod que valida los datos del CMS. Vive en @hwp/core-ui/schemas y es compartido por todos los clientes.

export const HeroBlockContent = z.object({
  title:    z.string().min(1),
  subtitle: z.string().optional(),
  image:    z.object({ src: z.string().url(), alt: z.string() }),
  cta:      z.object({ label: z.string(), href: z.string() }).optional(),
});

Layer 2 — Variants (cuando hay variaciones)

Tres sub-tipos según la complejidad:

TipoCuándoEjemplo
CVA (L2a)Solo cambia CSSMediaText: imageLeft / imageRight
Structural (L2b)Diferente DOM/hooksGallery: slider / masonry / grid
Functional (L2c)Diferentes campos por varianteGallery links vs Gallery grid

Layer 3 — Config Schema (cuando hay opciones de comportamiento)

Separado del content. Content es "qué ve el usuario". Config es "cómo se comporta el bloque".

export const GalleryBlockConfig = z.object({
  lightbox:  z.boolean().default(false),
  autoplay:  z.boolean().default(false),
  columns:   z.union([z.literal(2), z.literal(3), z.literal(4)]).default(3),
});

Layer 4 — Adapter (cuando conecta a un servicio externo)

El bloque no sabe si habla con THR, Masterbooking o Google Maps. Solo usa un hook (useBookingAdapter()) y el adapter concreto se inyecta via provider.

DominioBloquesProveedores
BookingBookingBlockTHR, Masterbooking, Witbooking
MapasMapBlockGoogle Maps, OSM, Mapbox
ReviewsReviewsBlockGoogle, TripAdvisor, manual
FormulariosFormBlockEmail, CRM, SendGrid

Decisión rápida: ¿qué capas necesita mi bloque?

  • ¿Solo renderiza contenido estático? → L1 solamente (RichTextBlock, BannerBlock)
  • ¿Tiene variaciones visuales o estructurales? → L1 + L2 (GalleryBlock, FAQBlock)
  • ¿Tiene opciones de comportamiento (autoplay, columnas)? → L1 + L2 + L3
  • ¿Conecta a un servicio externo? → L1 + L2 + L3 + L4 (BookingBlock, MapBlock)

Slots y personalización

Los slots son puntos de personalización visual dentro de un base-block. El bloque garantiza la estructura semántica (accesibilidad, SEO); el cliente decide cómo se ve cada pieza.

// Definición de slots en el base-block
export type HeroBlockSlots = {
  media?:   (image: ImageData) => React.ReactNode;
  heading?: (title: string, subtitle?: string) => React.ReactNode;
  cta?:     (cta: CtaData) => React.ReactNode;
};

// El base-block usa slots si los recibe, defaults si no
export function HeroBlock({ content, slots }: HeroBlockProps) {
  return (
    <section aria-labelledby="hero-heading">
      {slots?.media   ? slots.media(content.image)   : <DefaultMedia ... />}
      {slots?.heading ? slots.heading(content.title)  : <DefaultHeading ... />}
      {slots?.cta     ? slots.cta(content.cta)        : <DefaultCta ... />}
    </section>
  );
}
El bloque siempre pone el <section> y el aria-labelledby Los slots controlan lo visual. La estructura semántica (accesibilidad, SEO, HTML semántico) la garantiza el base-block — el cliente no puede romperla.

Tokens y cascade

Los tokens son los valores de diseño (colores, fuentes, espaciado, sombras) que hacen que un mismo bloque se vea diferente en cada cliente. Se resuelven en cascada: plataforma → semántico → marca.

🌍 Global (plataforma) — color.teal.600 = #0F6E56
↓ se mapea a
🏷️ Semántico — color.primary = {color.teal.600}
↓ el cliente overridea
🎨 Brand (tokens.json) — color.primary = #8B6914 (dorado)
↓ se compila a
📄 globals.css → :root { --color-primary: #8B6914; }
↓ Tailwind lo consume
🧱 Bloque usa bg-primary → se ve dorado

tokens.json del cliente

{
  "colors": {
    "background":   { "value": "#FFFFFF" },
    "surface":      { "value": "#E4F3F5" },
    "primary":      { "value": "#1A4A52" },
    "accent":       { "value": "#9FCAD0" },
    "text-on-dark": { "value": "#FFFFFF" },
    "border":       { "value": "rgba(159,202,208,0.35)" }
  },
  "fonts": {
    "heading": { "family": "Playfair Display", "fallback": "serif" },
    "body":    { "family": "Montserrat", "fallback": "sans-serif" }
  },
  "spacing": { "container-max": "1440px", "section-y": "clamp(3rem, 8vw, 6rem)" },
  "radii":   { "sm": "0.25rem", "md": "0.5rem", "lg": "1rem" },
  "shadows": { "card": "0 4px 12px rgba(0,0,0,0.06)" }
}
Regla: un componente NUNCA pone un color hexadecimal directo Siempre usa el token via clase Tailwind (bg-primary, text-accent). Así el mismo bloque se adapta automáticamente a cada cliente.

Reglas CSS

  • UN globals.css por cliente en src/app/globals.css. Contiene: @font-face, variables CSS de tokens, @keyframes, overrides de widgets externos (THR, Ideta), @media print.
  • CERO ficheros CSS por bloque. Los bloques solo usan clases Tailwind y recetas CVA. Nada de HeroBlock.css.
  • Tailwind v3 (DEC-012). No v4 hasta que el ecosistema (Next.js + CVA + Turborepo) sea estable.

SPECBOOT — Metodología

Spec-driven, Boot-strapped. La especificación va primero, el código va después. Nunca se escribe código sin una propuesta aprobada.

1️⃣ /enrich_us — Enriquecer la historia con detalles técnicos
↓
2️⃣ /propose — Diseñar la solución (qué ficheros, qué tests, qué riesgos)
↓
3️⃣ /apply — Implementar con TDD (test → fail → code → pass)
↓
4️⃣ /verify — Gates de calidad (typecheck, test, lint, build)
↓
5️⃣ /archive — Cerrar historia (actualizar docs, catálogo, marcar done)
↓
6️⃣ /commit — Conventional Commit en inglés
Regla: no se salta ningún paso Cada paso produce un artefacto que el siguiente consume. Si no hay propuesta aprobada, no se implementa. Si no pasa verify, no se archiva. Si no se archiva, no se commitea.

FAQ

¿Tengo que leer todos los docs antes de empezar?

No. Lee docs/guides/first-day-setup.md y docs/guides/project-map.md. El resto lo consultas según la tarea — docs/README.md te dice qué cargar en cada caso.

¿Puedo ignorar un skill y hacer algo manualmente?

Técnicamente sí, pero pierdes las garantías: el skill aplica las specs automáticamente. Si lo haces manual, tú eres responsable de verificar todo.

¿Diferencia entre bloque y composición?

Bloque: pieza visual reutilizable (hero, galería, formulario). Composición: montaje de bloques para una página de un cliente. El bloque es la pieza de LEGO; la composición es el modelo.

¿Qué pasa cuando se actualiza @hwp/core-ui?

Level 1 (re-export) recibe mejoras automáticamente con npm update. Level 2/3 solo se ven afectados si cambia el schema — eso es un major version bump que se comunica.

¿Por qué repos separados y no un monorepo con todo?

300 repos pequeños escalan mejor: CI independiente, deploys independientes, developers que solo clonan lo que necesitan, un bug nunca bloquea otro cliente (DEC-011).

¿Esto es como Scrum?

SPECBOOT define el ciclo de una historia individual, no la gestión de sprints. Se puede combinar con Scrum, Kanban, o lo que la empresa prefiera.
