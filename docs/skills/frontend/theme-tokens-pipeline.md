# Theme tokens pipeline — end-to-end walkthrough

> ✅ **Tailwind v4, CSS-first via `@theme` (DEC-017 — confirmed in hwe-core code).** Delivery is `@import "tailwindcss"` + `@import "@hwe/config/theme.css"` + a client `@theme {}` override in `globals.css`. There is **no JS preset**: `createhwePreset()` / `tailwind.config.ts` / `presets: [...]` were the Tailwind v3 API (DEC-012) and do not exist in `hwe-core`. `TokensContract` (Zod, `packages/core-ui/src/theme/tokens.contract.ts`) is kept as the build-time validation layer.
>
> The **how-to** for the design-token pipeline: how a color value in Figma reaches a CSS rule in the rendered page. Companion to [`../../contracts/frontend/theme-tokens.md`](../../contracts/frontend/theme-tokens.md) (the contract). Load this when bootstrapping a new client's theme, debugging a colour discrepancy, or onboarding a new developer.
>
> This is the practical walkthrough. The contract document is the source of truth for naming, validation rules, and the seasonized variant. Read the contract first if you are about to change the shape of `TokensContract`.

## Token cascade — the three-tier model

Before the five-stage pipeline, understand where each token value comes from. hwe resolves token values in three tiers at build time:

```
1. Global tokens    → platform-wide constants (raw palette, base spacing scale)
                      Lives in @hwe/core-ui — shared by all clients.

2. Semantic tokens  → role-based aliases (primary, surface, foreground...)
                      Also lives in @hwe/core-ui — what a token MEANS, not its value.

3. Brand tokens     → client-specific values for each semantic role
                      Lives in apps/site-{slug}/src/theme/tokens.json — the client's palette.
```

The cascade resolves **at build time**, not at runtime. When Tailwind compiles, it reads the brand tokens (`tokens.json`), which satisfy the semantic roles defined by `TokensContract`, which may reference global constants. The final CSS utility classes embed the resolved values — there is no runtime cascade.

> **One `globals.css` per client, zero CSS per block.** All client CSS lives in `apps/site-{slug}/src/app/globals.css`. Block files never contain CSS files — they use Tailwind utilities driven by the token cascade above.

## The five-stage pipeline

```
1. Figma          →  theme.css (Flavor A)  or scattered inline values (Flavor B)
2. Extraction     →  src/theme/tokens.json                     (brand tier)
3. Validation     →  TokensContract.parse(tokensJson)          (Zod, build-time)
4. Delivery       →  @theme {} in globals.css                  (over @hwe/config/theme.css base)
5. Tailwind v4    →  emits CSS custom properties + utility classes
```

Each stage has one input, one output, and one failure mode. Failures are loud (build errors, not silent visual drift).

## Stage 1 — Figma reference

The designer's Figma Make export lives at `figma-makes/{slug}/` (per [DEC-002](../../architecture/decisions.md#dec-002--one-figma-make-repo-per-client-tagged-per-import) — independent git repo, tagged per import, never edited).

Two flavors of exports exist:

### Flavor A — semantic token layer (preferred)

The export ships `src/styles/theme.css` with a `:root` block of semantic CSS custom properties:

```css
:root {
  --background: #FFFFFF;
  --foreground: #1A2E32;
  --primary:    #1A4A52;
  --accent:     #9FCAD0;
  /* ... */
}
```

And `src/styles/fonts.css` with the `@import` of Google Fonts (or self-hosted faces).

**Reference example:** `figma-makes/base-template/src/styles/theme.css` (Camping Mer et Camargue).

### Flavor B — scattered inline values

The export uses inline `style={{ color, background }}`, Tailwind arbitrary values (`bg-[#1A4A52]`), and per-file font declarations. There is no single source.

**Reference example:** `figma-makes/base-template/` (Flavor A) or any Figma Make export without a semantic token layer (Flavor B).

For Flavor B, the input is `docs/clients/{slug}/figma-analysis.md` (auto-generated by `/import-figma`), which aggregates the scattered values into a table.

### How to detect the flavor

Look for `figma-makes/{slug}/src/styles/theme.css`.
- It exists with a `:root` block → Flavor A.
- It does not exist (or has no semantic layer) → Flavor B.

## Stage 2 — Extraction to `tokens.json`

The output of this stage lives at `apps/site-{slug}/src/theme/tokens.json`. It is the **only place** where token values live for that client.

### Flavor A fast path (the case for the walking skeleton)

Map each `--name: value;` in `theme.css :root` onto the matching `TokensContract` key. Names usually align 1:1:

| `theme.css` CSS variable | `tokens.json` key |
|---|---|
| `--background`           | `colors.background`           |
| `--foreground`           | `colors.foreground`           |
| `--primary`              | `colors.primary`              |
| `--primary-foreground`   | `colors.primary-foreground`   |
| `--accent`               | `colors.accent`               |
| `--accent-foreground`    | `colors.accent-foreground`    |
| `--brand-teal`           | `colors.accent-secondary`     |
| `--secondary` / `--muted`| `colors.surface` (and `colors.secondary` if both are kept) |
| `--muted-foreground`     | `colors.muted-foreground`     |
| `--border`               | `colors.border`               |
| `--radius`               | `radii.lg` (and derived `sm`/`md` using `calc(var(--radius) - Npx)` if present) |

For fonts, read `theme.css @layer base` to see which elements use which family (`h1–h3` → heading, `body`/`button`/`input` → body/ui). Add CSS fallbacks yourself (`serif` for headings, `sans-serif` for body).

### Flavor B procedure

Open `docs/clients/{slug}/figma-analysis.md`. For each role required by `TokensContract`, copy the hex/rgba into the corresponding `tokens.json` field. See [`theme-tokens.md`](../../contracts/frontend/theme-tokens.md) §Flavor B procedure for the full steps.

### Resulting `tokens.json` shape

The shape is documented in [`theme-tokens.md`](../../contracts/frontend/theme-tokens.md) §`tokens.json` shape. The walking-skeleton example for the base-template:

```json
{
  "colors": {
    "background":         { "value": "#FFFFFF" },
    "foreground":         { "value": "#1A2E32" },
    "surface":            { "value": "#E4F3F5" },
    "primary":            { "value": "#1A4A52" },
    "primary-foreground": { "value": "#FFFFFF" },
    "accent":             { "value": "#9FCAD0" },
    "accent-foreground":  { "value": "#1A4A52" },
    "accent-secondary":   { "value": "#2A6A75" },
    "secondary":          { "value": "#E4F3F5" },
    "muted-foreground":   { "value": "#676977" },
    "border":             { "value": "rgba(159,202,208,0.35)" },
    "text-on-dark":       { "value": "#FFFFFF" }
  },
  "fonts": {
    "heading": { "family": "Playfair Display", "fallback": "serif" },
    "body":    { "family": "Montserrat",       "fallback": "sans-serif" },
    "ui":      { "family": "Montserrat",       "fallback": "sans-serif" }
  },
  "spacing": {
    "container-max": "1440px",
    "section-y":     "clamp(3rem, 8vw, 6rem)"
  },
  "radii": {
    "sm": "0.0625rem",
    "md": "0.1875rem",
    "lg": "0.3125rem"
  },
  "shadows": {
    "card":     "0 2px 20px rgba(26,74,82,0.09)",
    "elevated": "0 8px 30px rgba(0,0,0,0.12)"
  }
}
```

### Rules during extraction

- **Semantic roles, not visual descriptors.** `primary` not `teal`. `background` not `white`. The role name carries across clients; the value changes.
- **Snake-cased keys** for multi-word roles (`text-on-dark`, `accent-secondary`).
- **No invented values.** If `figma-analysis.md` does not surface a required role and `theme.css` does not declare it, stop and ask the designer.
- **`radii` defined in `tokens.json` describes available primitives, not where to use them.** The base-template defines `sm`/`md`/`lg` but applies `rounded` to almost nothing — the design uses rectangular surfaces. See [`block-creation.md`](./block-creation.md) §Design token rules, rule 2.

## Stage 3 — Validation via `TokensContract`

The contract lives at `packages/core-ui/src/theme/tokens.contract.ts`. It is a Zod schema that runs **at build time** to validate `tokens.json` before its values are expressed as `@theme` tokens.

```ts
import { z } from 'zod';

const ColorValue = z.object({ value: z.string() });
const FontValue  = z.object({ family: z.string(), fallback: z.string() });

export const TokensContract = z.object({
  colors: z.object({
    background:           ColorValue,
    foreground:           ColorValue.optional(),
    surface:              ColorValue,
    primary:              ColorValue,
    'primary-foreground': ColorValue.optional(),
    accent:               ColorValue,
    'accent-foreground':  ColorValue.optional(),
    'accent-secondary':   ColorValue.optional(),
    secondary:            ColorValue.optional(),
    'muted-foreground':   ColorValue.optional(),
    'text-on-dark':       ColorValue,
    border:               ColorValue,
    overlay:              ColorValue.optional(),
  }),
  fonts: z.object({
    heading: FontValue,
    body:    FontValue,
    ui:      FontValue.optional(),
  }),
  spacing: z.object({
    'container-max': z.string(),
    'section-y':     z.string(),
  }),
  radii:   z.record(z.string(), z.string()).optional(),
  shadows: z.record(z.string(), z.string()).optional(),
});

export type Tokens = z.infer<typeof TokensContract>;
```

Required fields are non-optional. If a client's `tokens.json` is missing `colors.primary`, `pnpm build` aborts with a Zod error pointing at the field — the site never reaches production with a broken palette.

The contract has known open questions (see [`theme-tokens.md`](../../contracts/frontend/theme-tokens.md) §Open contract questions) about whether to widen the required set (add `foreground`, split `surface` from `secondary`/`muted`). Until a DEC resolves them, the extracted tokens go in as-is and any mismatch is noted in `docs/clients/{slug}/figma-notes.md`.

## Stage 4 — Delivery via `@theme` (Tailwind v4)

Token values reach the browser through CSS, not a JS preset. `@hwe/config/theme.css` declares the base `@theme` namespace; the client's `globals.css` imports it and overrides only the roles that differ:

```css
/* src/app/globals.css */
@import "tailwindcss";
@import "@hwe/config/theme.css";   /* base @theme tokens */

@theme {
  --color-primary: #1a4a52;
  --color-accent:  #9fcad0;
  --font-heading:  "Playfair Display", Georgia, serif;
  --font-body:     "Montserrat", system-ui, sans-serif;
  --spacing-section-y: 80px;
  --width-container: 1280px;
}
```

`tokens.json` + `TokensContract` stay as the **validation layer** (Stage 3): the extracted values are validated by Zod, then expressed as the `@theme` overrides above. Whether that `@theme` block is generated from `tokens.json` or authored from it is a build detail owned by hwe-core; the contract ([`theme-tokens.md`](../../contracts/frontend/theme-tokens.md)) is the source of truth.

## Stage 5 — Tailwind v4 emits CSS

Tailwind v4 reads the `@theme` declarations and emits CSS custom properties + utility classes: `text-primary`/`bg-primary` resolve to `--color-primary`, `rounded-md` to `--radius-md`, `shadow-card` to `--shadow-card`. There is **no `tailwind.config.ts` and no `presets: [...]`**.

> **Cross-package utilities:** blocks consumed from `@hwe/core-ui` use Tailwind utility classes; the build's source scan must include the core-ui sources, otherwise those blocks render unstyled (no CSS emitted for their classes). See [`theme-tokens.md`](../../contracts/frontend/theme-tokens.md) for the current v4 source-scan setup.

### Fonts via `next/font/google`

The `@theme` block declares `--font-heading` and `--font-body` with the **declared family names** from `tokens.json`. Loading the actual font is a separate concern handled by Next.js:

```tsx
// apps/site-{slug}/src/app/layout.tsx
import { Montserrat, Playfair_Display } from 'next/font/google';

const montserrat = Montserrat({
  subsets: ['latin'],
  weight: ['400', '500', '600', '700'],
  variable: '--font-montserrat',
  display: 'swap',
});

const playfair = Playfair_Display({
  subsets: ['latin'],
  weight: ['400', '500', '600', '700'],
  variable: '--font-playfair',
  display: 'swap',
});

export default function RootLayout({ children }) {
  return (
    <html lang="fr" className={`${montserrat.variable} ${playfair.variable}`}>
      <body className="bg-background text-foreground">{children}</body>
    </html>
  );
}
```

`next/font` self-hosts the font faces (no public CDN at runtime, matches the rule in [`theme-tokens.md`](../../contracts/frontend/theme-tokens.md) §Fonts) and exposes them as CSS custom properties (`--font-montserrat`, `--font-playfair`).

In `globals.css`, apply the fonts at the base layer:

```css
@tailwind base;
@tailwind components;
@tailwind utilities;

@layer base {
  html {
    font-family: var(--font-montserrat), system-ui, sans-serif;
  }
  h1, h2, h3 {
    font-family: var(--font-playfair), Georgia, serif;
    font-weight: 600;
    line-height: 1.25;
  }
}
```

Tailwind utilities like `font-heading` (which expands to `font-family: 'Playfair Display', serif`) coexist with the base layer — the browser resolves either through the same loaded font face.

### Emitted CSS — what to expect

After the dev server compiles, the CSS at `/_next/static/css/app/layout.css` contains:

- One utility per token color (e.g. `.bg-primary { background-color: rgb(26 74 82 / var(--tw-bg-opacity, 1)); }`).
- `.max-w-container { max-width: 1440px; }`, `.py-section-y { padding-top: clamp(3rem, 8vw, 6rem); ... }`.
- `.shadow-card { --tw-shadow: 0 2px 20px rgba(26,74,82,0.09); ... }`.
- `@font-face` rules emitted by `next/font` for each weight × subset × style (≈38 rules for Montserrat + Playfair Display × 4 weights).

If a utility is missing in the emitted CSS, the cause is almost always: the source file using it is not covered by Tailwind v4's source scan (the core-ui sources are not included).

## Verification — confirming the pipeline reaches the browser

When you suspect a token is not flowing through, run these checks in order:

```bash
# 1. Tokens parse?
cd site-{slug}
pnpm typecheck                    # TokensContract.parse(tokens.json) fails loud if not

# 2. Utility classes emitted?
curl -s "http://localhost:3000/_next/static/css/app/layout.css?v=<n>" \
  | grep -A1 "\.bg-primary\b"     # should show the rgb() value from tokens.primary

# 3. Font face loaded?
curl -s "http://localhost:3000/_next/static/css/app/layout.css?v=<n>" \
  | grep -c "@font-face"          # should be ≥ 8 (one per weight, two families minimum)

# 4. Probe page renders with the values?
curl -s http://localhost:3000     # check class names are in the HTML
```

If step 1 fails, the schema/tokens.json mismatch is loud (Zod error). If step 2 fails, check that Tailwind v4's source scan covers the core-ui sources. If step 3 fails, check `next/font` import in `layout.tsx`. If step 4 fails, restart the dev server (HMR sometimes misses CSS `@theme` changes).

## Seasonized clients

The seasonized variant (per [DEC-005](../../architecture/decisions.md#dec-005--per-season-theme-tokens-for-clients-with-hasseasons)) is **not** active in the walking skeleton — `site-demo` is single-theme. The contract supports both shapes (single `tokens.json` vs `tokens-{season}.json` per season); the pipeline switches behavior based on which files exist. See [`theme-tokens.md`](../../contracts/frontend/theme-tokens.md) §Seasonized clients for the full mechanism.
