# Theme tokens

> **How** design tokens flow from Figma to the rendered page. Companion to the rules in [`../../specs/frontend/frontend-standards.md`](../../specs/frontend/frontend-standards.md) and [`../../specs/frontend/block-architecture.md`](../../specs/frontend/block-architecture.md).
> Load this file when scaffolding a new client's theme, exporting tokens from Figma, or debugging a visual inconsistency between Figma and the rendered site.
>
> **Token names and semantic roles below** (`color/primary`, `font/heading`) **are a starting convention.** The final naming taxonomy may be revised once the designer and the agency have processed several clients — flag changes in `decisions.md`.
>
> ✅ **Tailwind v4, CSS-first via `@theme` (DEC-017 — confirmed in hwe-core code).** The pipeline is: Figma → `tokens.json` → **`TokensContract` (Zod, build-time validation — kept)** → values delivered via **`@theme` CSS** (`@hwe/config/theme.css` base + a client `@theme {}` override in `globals.css`). There is **no JS preset**: `createhwePreset()` / `tailwind.config.ts` / `presets: [...]` were the Tailwind v3 API (DEC-012) and **do not exist anywhere in `hwe-core` code**. The earlier "open question" (does `TokensContract` survive in v4?) is resolved: it does — `packages/core-ui/src/theme/tokens.contract.ts` is the live contract.

## The flow

```
1. Designer defines Figma Variables for the client                   (Figma)
   color/primary/default = #1A4A52
   color/accent/default  = #9FCAD0
   font/heading          = "Playfair Display"
   ...
        ↓
2. The Figma Make export materializes these — modern exports already  (Figma → repo)
   ship them as semantic CSS custom properties (src/styles/theme.css
   :root + @theme inline). We map that layer → tokens.json.
        ↓
3. Token file lives at src/theme/tokens.json (in the client repo)    (in client repo)
        ↓
4. tokens.json must satisfy TokensContract type from @hwe/core-ui    (TS validation)
        ↓
5. src/app/globals.css uses @import "tailwindcss" + @import          (Tailwind v4)
   "@hwe/config/theme.css" and overrides with @theme { ... } blocks
        ↓
6. Tailwind v4 emits CSS custom properties and utility classes       (build)
        ↓
7. @hwe/core-ui components render using the tokens                   (runtime)
```

The contract is the load-bearing piece: it is what keeps a misnamed Figma Variable from silently breaking the site.

## Token extraction — interim manual process

> Figma Make repos never ship a `tokens.json` or a Tailwind config in the hwe shape, so producing the consumable `tokens.json` is **today a manual step**. But not all exports are equally messy — there are two flavors, and which one you got decides how much work the extraction is:
>
> - **Flavor A — semantic token layer (preferred, e.g. `base-template` / Camping Mer et Camargue).** The export ships `src/styles/theme.css` with a `:root` block of semantic CSS custom properties (`--primary`, `--accent`, `--muted`, `--foreground`, `--radius`…), an `@theme inline` block exposing them as Tailwind utilities, and `src/styles/fonts.css` for the font `@import`. Extraction is near-mechanical: read `:root`, map each variable to the matching `TokensContract` role.
> - **Flavor B — scattered inline values.** Colors live in inline `style={{ color, background }}`, Tailwind arbitrary values (`bg-[#...]`), and font declarations sprinkled across `.tsx` files. There is no single source; extraction means scraping and de-duplicating by hand. `/import-figma`'s analysis already aggregates these into `figma-analysis.md`, which is your starting point.
>
> Always check for Flavor A first (`src/styles/theme.css`); fall back to the Flavor-B scraping procedure only when there is no semantic token layer.
>
> A `/extract-tokens <slug>` skill will be born once we have done this manually across both flavors — that way the skill is built from real patterns, not guesses. Until then, follow the procedure below by hand.

### Inputs

- `figma-makes/{slug}/src/styles/theme.css` — **Flavor A only.** The `:root` block (semantic CSS custom properties) and `@theme inline` block. This is the authoritative source when it exists.
- `figma-makes/{slug}/src/styles/fonts.css` — **Flavor A only.** The font `@import` (family names + weights).
- `docs/figma-analysis.md` (in client repo or `hwe-tools/docs/clients/{slug}/`) — auto-generated by `/import-figma`. Contains a table of colors with role / hex / main files, and a table of fonts with role / family. The primary source for **Flavor B**, and a useful cross-check for Flavor A.
- `figma-makes/{slug}/` — the source Figma Make repo, in case the analysis is incomplete and you need to re-scan.

### Output

`src/theme/tokens.json` (in client repo) — must satisfy `TokensContract` (see "The contract" below).

### Step 0 — detect the flavor

Look for `figma-makes/{slug}/src/styles/theme.css`.

- **It exists with a `:root` block of `--`-prefixed semantic variables → Flavor A.** Use the fast path below.
- **It does not exist (or has no semantic token layer) → Flavor B.** Use the scraping procedure.

### Flavor A fast path (semantic token layer)

1. **Read `theme.css` `:root`.** Each `--name: value;` is a candidate token. Map by semantic role to the `TokensContract` key — the names usually align almost 1:1 (`--primary` → `primary`, `--accent` → `accent`, `--border` → `border`, `--radius` → `radii`).
2. **Resolve role mismatches explicitly.** The export's role set will not match `TokensContract` perfectly. Map and record the mapping in `figma-notes.md`. Known cases from `base-template`:
   - `--secondary` / `--muted` (same value) → `colors.surface` *or* a muted background, depending on usage — inspect which the components use.
   - `--foreground` (main text color, e.g. `#1A2E32`) → there is **no plain `text` role in `TokensContract` today** (it only has `text-on-dark`). Flag this gap (see "Open contract questions") rather than forcing the value into the wrong key.
   - The `.dark` block, if present but generic (neutral oklch greys, not brand-tuned), is **not designed** — ignore it for extraction.
3. **Fonts**: read `fonts.css` for the families and `theme.css` `@layer base` for which element uses which (`h1–h3` → heading, `body`/`button`/`input` → body/ui). Add the CSS fallback yourself.
4. **Spacing / radii**: `container-max` from the repeated `max-w-[Npx]` (here `1440px`); `--radius` maps to `radii`; `section-y` stays the `clamp(3rem, 8vw, 6rem)` default unless the design shows otherwise.
5. **Validate** with `TokensContract.parse(...)` (see step 7 of the Flavor-B procedure — identical).

### Flavor B procedure (scattered inline values)

1. **Open `figma-analysis.md` of the client.** Identify the role columns (`background`, `primary`, `accent`, `text-on-dark`, `surface`, `border`, `overlay`...).
2. **For each role required by `TokensContract`**, copy the hex / rgba value from the analysis into the corresponding field of `tokens.json`. Use the role name as the JSON key.
3. **For each role marked optional in `TokensContract`** (e.g. `accent-secondary`, `overlay`), include only if the analysis surfaced it. Do not invent values.
4. **Fonts**: copy `family` and add a CSS-compliant `fallback` (`serif` for heading-style fonts, `sans-serif` for body/ui). The analysis usually does not specify the fallback; it is your call.
5. **Spacing**: `container-max` comes from the analysis's "Layout" section (the `max-w-[Npx]` value). `section-y` is a sensible default — `clamp(3rem, 8vw, 6rem)` — unless the design shows a clearly different vertical rhythm.
6. **Radii and shadows**: extract from the analysis if present; otherwise default to the placeholder values shown in "`tokens.json` shape" below and refine after a visual pass against Figma Make.
7. **Validate**: in a quick scratch file or REPL, run `TokensContract.parse(yourTokensJson)`. Iterate until it passes. If a required key is missing in the analysis, **stop and ask the designer** — never make up a brand color.

### Naming conventions while extracting

- Use the **semantic role** (`primary`, `accent`) as the JSON key, not the visual descriptor (`brown`, `sage`). The analysis already does this in most cases.
- If the analysis uses a different name (e.g. `cream` instead of `background`), translate to the contract's name and note the mapping in `docs/clients/{slug}/figma-notes.md` so the next person knows.
- Hex values are uppercase (`#5B5446`, not `#5b5446`). Rgba values preserve the source format.

### When to promote this to `/extract-tokens` skill

After doing this manually for both flavors (Flavor A: `base-template`; Flavor B: a Figma Make export without a semantic token layer), evaluate:

- How many decisions during the process were mechanical (always the same answer)? Those are skill rules. The Flavor-A fast path is almost entirely mechanical — strong skill candidate.
- How many required human judgment (mapping ambiguous role names, choosing fallbacks, resolving the role mismatches in step 2)? Those become skill prompts that ask the user.
- How long did it take per flavor? Flavor A should be near-instant; if Flavor B is over 30 minutes per client, the skill is mandatory before client #3.

The decision and the skill spec, when ready, get registered in `docs/catalog.md` and documented in a new DEC.

## `tokens.json` shape

The file is the **only place** where token values live. Components never hardcode hex codes or font names.

> Example below uses `base-template` (Camping Mer et Camargue), mapped from its `theme.css` `:root` via the Flavor-A fast path.

```json
{
  "colors": {
    "background":       { "value": "#FFFFFF" },
    "surface":          { "value": "#E4F3F5" },
    "primary":          { "value": "#1A4A52" },
    "accent":           { "value": "#9FCAD0" },
    "accent-secondary": { "value": "#2A6A75" },
    "text-on-dark":     { "value": "#FFFFFF" },
    "border":           { "value": "rgba(159,202,208,0.35)" },
    "overlay":          { "value": "rgba(26,74,82,0.55)" }
  },
  "fonts": {
    "heading": { "family": "Playfair Display", "fallback": "serif" },
    "body":    { "family": "Montserrat",       "fallback": "sans-serif" },
    "ui":      { "family": "Montserrat",       "fallback": "sans-serif" }
  },
  "spacing": {
    "container-max": "1440px",
    "section-y":     "clamp(3rem, 8vw, 6rem)"
  },
  "radii": {
    "sm": "0.25rem",
    "md": "0.5rem",
    "lg": "1rem",
    "full": "9999px"
  },
  "shadows": {
    "card":      "0 4px 12px rgba(0,0,0,0.06)",
    "elevated":  "0 12px 32px rgba(0,0,0,0.12)"
  }
}
```

Rules:

- **Semantic roles, not literal names.** `primary` not `brown`. `background` not `cream`. The same token name carries across clients with different values.
- **Snake-cased keys** when the role is multi-word (`text-on-dark`, `accent-secondary`).
- **Values are strings** (hex, rgba, CSS length, font family). Numbers only for unit-less things (line height multipliers, opacity).
- **No nested overrides** per breakpoint or per state inside `tokens.json`. Responsive and stateful behavior is the component's job, not the token's.
- **No client-specific keys.** A client that needs an extra color introduces it via a per-client composition or an extra block, not a new token role in `tokens.json`.

## The contract (`@hwe/core-ui/src/theme/tokens.contract.ts`)

```ts
// packages/core-ui/src/theme/tokens.contract.ts
import { z } from 'zod';

const ColorValue = z.object({ value: z.string() });
const FontValue  = z.object({ family: z.string(), fallback: z.string() });

export const TokensContract = z.object({
  colors: z.object({
    background:        ColorValue,
    surface:           ColorValue,
    primary:           ColorValue,
    accent:            ColorValue,
    'accent-secondary': ColorValue.optional(),
    'text-on-dark':    ColorValue,
    border:            ColorValue,
    overlay:           ColorValue.optional(),
  }),
  fonts: z.object({
    heading: FontValue,
    body:    FontValue,
    ui:      FontValue.optional(),
  }),
  spacing: z.object({
    'container-max': z.string(),
    'section-y':     z.string(),
  }),
  radii: z.record(z.string(), z.string()).optional(),
  shadows: z.record(z.string(), z.string()).optional(),
});

export type Tokens = z.infer<typeof TokensContract>;
```

`tokens.json` is parsed against this schema **at build time**. A client whose Figma export is missing `colors.primary` fails the build instead of producing a broken site. Required vs optional keys are explicit.

### Open contract questions (raised by `base-template`)

Mapping the Mer et Camargue export (Flavor A) onto `TokensContract` surfaced gaps. These are **not yet decided** — they need a DEC before the contract changes:

- **No plain text color role.** The contract has `text-on-dark` but no `text` / `foreground` for body copy on light backgrounds. `base-template` defines `--foreground: #1A2E32` and uses it everywhere. Today there is nowhere correct to put it. Candidate fix: add a required `foreground` (or `text`) color role.
- **`surface` vs `secondary`/`muted`.** Modern shadcn-style exports separate `--secondary`, `--muted`, and `--card`; the contract only has `surface`. Decide whether to collapse them into `surface` or widen the contract.
- **`radii` is a flat map but exports define a single `--radius` + derived steps.** Decide whether to accept a single base radius and derive sm/md/lg, matching the export convention.

Until a DEC resolves these, extractors record the mapping/omission in the client's `figma-notes.md` and do not force values into the wrong key.

## Per-client `globals.css` (Tailwind v4)

Tailwind v4 uses CSS-first configuration. Token values flow through `src/app/globals.css`:

```css
@import "tailwindcss";
@import "@hwe/config/theme.css";   /* base hwe design tokens */

/* Client overrides — shadow the base tokens */
@theme {
  --color-primary: #1a4a52;
  --color-primary-foreground: #ffffff;
  --color-accent: #9fcad0;
  --font-heading: "Playfair Display", Georgia, serif;
  --font-body: "Montserrat", system-ui, sans-serif;
  --spacing-section-y: 80px;
  --width-container: 1280px;
}
```

`@hwe/config/theme.css` defines the base token namespace. Client repos shadow only the values that differ from the platform defaults.

> **No `tailwind.config.ts` + `createhwePreset()`** — that was the Tailwind v3 API. v4 configures entirely via CSS.

## CSS custom properties (`@hwe/core-ui/src/theme/cssVariables.ts`)

Tailwind's `@theme` directive (v4) emits CSS custom properties for the values in the config. Components can reference them directly when needed (e.g. animations, inline styles for runtime-dynamic values):

```css
/* generated by Tailwind from the preset */
:root {
  --color-primary: #1A4A52;
  --color-accent: #9FCAD0;
  --font-heading: "Playfair Display", serif;
  /* ... */
}
```

The `cssVariables.ts` helper exposes typed accessors so component code does not stringly-type these names:

```ts
// packages/core-ui/src/theme/cssVariables.ts
export const cssVar = {
  color: {
    primary:    'var(--color-primary)',
    accent:     'var(--color-accent)',
    background: 'var(--color-background)',
    // ...
  },
  font: {
    heading: 'var(--font-heading)',
    body:    'var(--font-body)',
  },
} as const;
```

Use the helper instead of writing the string literal `'var(--color-primary)'` in component code.

## Fonts

- Self-host via `next/font` in `apps/site-{slug}/src/theme/globals.css` (or via `next/font/local` if the client provides custom font files).
- Family names in `tokens.json` are the **declared family**, what Tailwind references. The loading mechanism is separate.
- Fonts go in `apps/site-{slug}/public/fonts/` if self-hosted from files.
- Never load fonts from a public CDN at runtime in production.

## Per-client overrides without forking core-ui

If a client needs visual behavior not expressible via tokens (e.g. a unique header pattern), the answer is:

1. **First** try declaring a new variant on the relevant block.
2. **Second**, if a variant is not enough, build a per-client composition wrapping the block.
3. **Never** import the block and modify its CSS via global selectors targeting it. That breaks isolation across clients.

## Seasonized clients — `hasSeasons` feature (per DEC-005)

The single-`tokens.json` layout above is the **default** and covers ~90%+ of hwe clients. Clients that opt into the `hasSeasons` feature (typically `residencia-vacacional` type, sometimes `hotel` / `rural`) have **N tokens files**, one per declared season.

See `docs/architecture/domain-model.md` §8 for the full seasonality model. The relevant points for theming:

- A client declares N `Season` entities in Payload (`winter`, `summer`, `christmas`, `easter`, custom).
- For each season, the designer exports a separate Figma variable set.
- The active season is decided server-side (in v1, by current date matching the season's `dateRanges`) and emitted on the `<html data-season="winter">` attribute.

### File layout for seasonized clients

```
apps/site-{slug}/src/theme/
├── tokens-winter.json         ← one file per season slug
├── tokens-summer.json
├── tokens-christmas.json      ← arbitrary slug, defined by the client's Season entities
└── globals.css                ← @theme base + per-season @theme overrides (scoped by [data-season])
```

The build pipeline auto-detects the mode by file presence:

- If `tokens.json` exists → **single-theme mode** (default).
- If any `tokens-*.json` files exist (and no `tokens.json`) → **seasonized mode**.
- Both present → **error at build time** (ambiguous configuration).

### Updated `TokensContract` accepts both shapes

```ts
// packages/core-ui/src/theme/tokens.contract.ts
import { z } from 'zod';

const SingleTokens = TokensSchema; // the schema shown above

const SeasonizedTokens = z.record(
  z.string().regex(/^[a-z0-9-]+$/),  // season slug
  TokensSchema
);

export const TokensContract = z.union([SingleTokens, SeasonizedTokens]);
export type Tokens = z.infer<typeof TokensContract>;
```

Under Tailwind v4 the seasonized values are emitted as `@theme`/CSS-variable blocks scoped by season, so one CSS bundle carries all seasons and the active one is selected at runtime via the `[data-season="..."]` attribute on `<html>`:

```css
/* globals.css (seasonized client) */
@import "tailwindcss";
@import "@hwe/config/theme.css";

@theme { /* base / default season */ --color-primary: #1a4a52; }
:where([data-season="winter"]) { --color-primary: #2a3a6a; }
:where([data-season="summer"]) { --color-primary: #1a4a52; }
```

### Runtime — how a block reads the active season

The active season slug is set on the `<html>` tag by the root layout at build time (since static export). Components do not need to read it explicitly — Tailwind's `:where([data-season="winter"])` selectors apply automatically.

When a block has **content** that is also seasonized (text, image), the block reads the active season from a React context provided by the root layout:

```tsx
// in a block that renders seasonized content
const season = useActiveSeason(); // from @hwe/core-ui
return <p>{content.body[season] ?? content.body.default}</p>;
```

The `useActiveSeason()` hook is defined in `@hwe/core-ui/src/theme/season.ts` and reads from the same `data-season` attribute the build emitted.

### What does NOT change

- The `TokensContract` is still the single source of validation. A bad seasonized file fails the build with the same Zod error as a bad single file.
- The token names (`primary`, `accent`, `background`, etc.) are identical across seasons — the values differ, the keys do not.
- `cssVariables.ts` accessors do not change — they still read `--color-primary`; the `data-season` selectors decide which value resolves.
- Self-hosted fonts work the same way.

### Migration single → seasonized

A client that adds `hasSeasons` after launch:

1. Rename `tokens.json` → `tokens-{defaultSeasonSlug}.json` (e.g. `tokens-summer.json` if launching in summer).
2. Add the additional season files (`tokens-winter.json`, etc.) with the designer's new exports.
3. Declare the `Season` entities in Payload.
4. Rebuild — pipeline auto-detects the seasonized mode.

No code changes required outside the theme folder and Payload data.

## Token cascade (DEC-015)

The three-layer cascade (global → semantic → brand) flows entirely through Tailwind v4 `@theme` CSS — see [§Per-client `globals.css`](#per-client-globalscss-tailwind-v4):

```
global tokens          →  semantic tokens          →  brand tokens
(spacing, radii,          (color roles: primary,       (client values:
 shadows defaults)         accent, surface, …)          #1A4A52, "Playfair Display", …)
        ↓                         ↓                              ↓
  @hwe/config                @hwe/core-ui                 globals.css @theme
  theme.css (@theme)         TokensContract (Zod)         (per-client override)
```

- **Global tokens** are the platform defaults declared in `@hwe/config/theme.css` (`@theme` base): base spacing scale, default radii, base shadow values. They are never client-specific.
- **Semantic tokens** are the roles declared in `TokensContract` (`primary`, `accent`, `surface`, `text-on-dark`, …). They are named by function, not by color. Core-ui components reference semantic tokens only — never raw hex.
- **Brand tokens** are the client values in `tokens.json`. They satisfy the semantic roles for a specific client.

`@hwe/config/theme.css` provides the base layer. The client's `@theme {}` block in `globals.css` overrides the specific tokens. Components never perform runtime token resolution.

### `globals.css` rule

There is exactly **ONE** `globals.css` per client, located at:

```
apps/site-{slug}/src/app/globals.css
```

This file contains:

- `@tailwind base / components / utilities` (or `@import "tailwindcss"` in v4).
- `@theme` directives for font loading.
- Any global CSS reset specific to this client.

**Zero CSS files per block.** Blocks style themselves exclusively through Tailwind utility classes (resolved from tokens via the preset). A block that ships its own `.css` file is in violation of this rule.

## What NOT to do

- Don't put hex codes in component code. Use the token via a class name or `cssVar`.
- Don't add a `tokens.json` field that no component reads. Dead tokens hide the real design intent.
- Don't override tokens at the route/page level (`<div style={{ '--color-primary': '...' }}>`). If a route needs a different color, the design has not been thought through.
- Don't share `tokens.json` between clients. Each client gets its own.
- Don't fork `@hwe/config/theme.css` per client. Override the base tokens in the client's own `@theme {}` block in `globals.css`; if you need a deviation the base doesn't allow, tell the team why (DEC entry).
- Don't add a `globals.css` inside a block folder or any `packages/core-ui/` subfolder. One file, one place: `src/app/globals.css` in the client repo.
