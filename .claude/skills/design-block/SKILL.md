# Design Block

## When to use

When you need to create a block for a client but there is NO Figma design for it. The designer delivered base pages but this specific block/page was not included.

## Prerequisites

- `docs/design-language.md` in the client repo (or `hwe-tools/docs/clients/{slug}/design-language.md` if repo not yet created) MUST exist. If not → tell the user: "Run `/import-figma` first to extract the design language, then re-run `/design-block`."
- `src/theme/tokens.json` in the client repo MUST exist.
- At least 2 blocks already implemented in `src/blocks/` of the client repo. If fewer than 2 exist → tell the user: "Not enough implemented blocks to detect patterns. Implement at least 2 base blocks first."

## Process

### Step 1 — Verify prerequisites

Check that all three prerequisites exist. If any is missing, stop with the appropriate message above. Do not attempt to generate a spec without them.

### Step 2 — Read context

Load the following in parallel:
- `docs/design-language.md` (client repo) — the visual contract
- `src/theme/tokens.json` (client repo) — the resolved token values
- 2–3 block implementations from `src/blocks/` (client repo) — pick the most visually rich ones (prefer blocks with cards, images, or complex layouts over simple text blocks)
- `docs/specs/frontend/block-architecture.md` §4-layers — to determine which layers the new block needs

### Step 3 — Invoke ux-ui-analyst in Mode B

Spawn a sub-agent (Agent tool) with the ux-ui-analyst system prompt in Mode B:

Pass:
- Block name
- Full content of `design-language.md`
- Full content of `tokens.json`
- Full content of 2–3 existing block implementations

Receive: the visual specification document.

### Step 4 — Save the spec

Create directory `docs/block-specs/` in the client repo if it does not exist.

Save the spec as `docs/block-specs/{BlockName}.visual-spec.md` with this header:

```markdown
# Visual spec — {BlockName} ({ClientName})

> DRAFT — requires human review before implementation.
> Generated by /design-block on {date}.
> Design language reference: docs/design-language.md
> Run /propose {BlockName} once this spec is approved.
```

### Step 5 — Print summary

```
Visual spec created: docs/block-specs/{BlockName}.visual-spec.md
Status: DRAFT — review and approve before /propose
Design language reference: docs/design-language.md
Layers recommended: {L1 / L2 / L3 as specified in the spec}

Next step:
  1. Review the spec — check it matches the site's visual style
  2. Approve it (or edit it)
  3. Run: /propose {BlockName}  (planner will use the spec as visual input)
```

## After approval

Once the human approves the visual spec, the normal SPECBOOT cycle continues:

```
/propose {BlockName}
    → planner reads the visual spec as input (docs/block-specs/{BlockName}.visual-spec.md)
/apply
    → implementer follows the spec's Tailwind classes and patterns
/verify
    → verifier runs CI gates
ux-ui-analyst Mode B re-invoked
    → verifies the implementation matches the approved spec
```

## Refusal cases

- `design-language.md` does not exist → refuse with: "Run `/import-figma {git-url} {slug}` first to extract the design language, then re-run `/design-block`."
- `tokens.json` does not exist → refuse with: "No tokens.json found for this client. Run `/import-figma` and extract tokens first."
- Fewer than 2 existing blocks → refuse with: "Not enough implemented blocks to detect patterns. Implement at least 2 base blocks (via `/scaffold-block --target client`) first."
- Asked to produce code — redirect: "This skill produces a visual spec only. Run `/propose {BlockName}` after approving the spec to get the implementation plan."
